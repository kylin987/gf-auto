# 闲鱼客户端状态检测设计

## 1. 目标

在闲鱼客户端新增独立一级菜单“状态检测”，位于“软件更新”上方。用户点击“立即检测”后，客户端对本机环境、Gateway 连接和各店铺实例做一次只读检测，提前发现会导致漏消息、无法回复、无法改价或无法发货的问题。

状态检测不在后台定时运行，不主动弹窗，不自动重连或重新登录。检测结果提供明确处理建议；只有用户点击处理按钮后才执行对应动作。

## 2. 范围

涉及：

- `gf-auto`：检测编排、闲鱼账号权限探测、结果展示和处理按钮。
- `yhs-plugin-gateway`：提供当前登录用户范围内的轻量诊断接口。

不涉及：

- 不修改 `yhs-bus`。
- 不新增数据库表，不保留检测历史。
- 不建设后台监控、定时巡检或主动告警。
- 不读取防火墙配置并作推断，只根据真实网络连接结果提示可能原因。

## 3. 页面结构

左侧导航顺序为：

1. 运行概览
2. 店铺管理
3. 运行日志
4. 状态检测
5. 软件更新
6. 设置

状态检测页从上到下显示：

1. 页面标题、上次检测时间和“立即检测”按钮。
2. 总体结论：正常、提醒、异常和未完成的数量及最重要问题。
3. 本机环境检测结果。
4. 按店铺分组的实例检测结果。

结果状态：

- `normal`：不影响当前业务。
- `warning`：暂未中断，但需要关注。
- `error`：当前可能漏消息、无法回复、无法改价或无法发货。
- `unknown`：因超时或依赖不可用而无法判断，不能误报为权限不足。

总体状态取所有已完成检测项中的最严重状态；存在 `unknown` 时单独显示未完成数量。

## 4. 客户端设计

### 4.1 组件边界

新增 `status_diagnostics.py`，负责：

- 并行执行单项检测。
- 为每项检测设置超时并隔离异常。
- 统一生成检测项和店铺分组结果。
- 计算总体状态。

`dashboard.py` 只负责新增菜单、渲染检测进度与结果、触发用户明确选择的处理动作。检测在工作线程中执行，Tkinter 主线程只做界面更新。检测期间禁用“立即检测”，避免重复并发。

`XianyuLive` 和 `GatewayClient` 提供只读状态快照，不允许检测器修改连接、登录或执行器状态。

### 4.2 本机检测项

- 客户端版本：调用现有更新检查；有新版为提醒。
- 网络与 DNS：分别验证闲鱼接口域名和插件网关，区分网络故障与登录失效。
- Chrome：可执行文件存在且可访问，各实例 Chrome Profile 目录可写。
- 本地数据：配置、Cookie、日志目录和 Outbox SQLite 可读写。
- 本地接口：运行中的实例对应端口可连接。
- Gateway Token：存在、未过期，并能通过诊断接口鉴权。
- Gateway WebSocket：每个运行实例当前是否已连接并完成绑定。
- Outbox：汇总每个实例的待补发和阻塞事件。无积压为正常；存在短时待补发为提醒；最老事件超过 10 分钟为异常。

文件写权限通过在目标目录创建并删除临时文件检测。SQLite 只执行最小读写能力检查，不修改业务记录。

### 4.3 店铺检测项

- 店铺仍在当前 SaaS 子账号授权范围。
- 店铺实例是否已启动。
- 当前闲鱼账号与绑定店铺是否匹配。
- Cookie 登录态是否有效。
- 闲鱼 IM WebSocket 是否连接。
- 商品管理权限：复用商品列表只读接口，按 `pageSize=1` 请求。接口成功即有权限，即使商品为空；仅明确的无权限响应判定为异常。网络失败和登录过期分别归入网络或登录检测，权限结果为 `unknown`。
- 本机实例是否为当前店铺执行器。
- 同店铺在线设备数量；超过一台判定异常并提示关闭其他电脑上的同一实例。
- 最近 30 分钟发送消息、查询订单、改价和发货任务是否存在未恢复失败。若失败后同店铺同任务类型已有成功记录，显示“已恢复”，不继续报警。

### 4.4 处理动作

首版只复用已有明确动作：

- 启动实例。
- 重新登录当前店铺。
- 检查更新。
- 查看处理建议。

双机冲突、账号无商品管理权限等不能由软件安全修复的问题，只展示具体处理建议。

## 5. Gateway 设计

新增客户端鉴权接口，例如：

```text
POST /api/v1/client/diagnostics
Authorization: Bearer <accessToken>
```

请求只包含本机实例标识：

```json
{
  "instances": [
    {"storeId": 203, "instanceId": "store-xxxx"}
  ]
}
```

Gateway 必须从 Token 获取 `pubId`、`deviceId` 和 `storeIds`，忽略客户端提供的权限范围。请求中的 `storeId` 不在 Token 授权范围时不返回该店铺数据。

每个店铺返回：

- 是否仍被当前账号授权。
- 当前有效执行器的实例标识及本机是否匹配。
- 当前在线连接数和去重后的在线设备数。
- 最近 30 分钟关注任务的最终状态、最后失败原因及是否已恢复。

接口使用现有 `Show` 响应格式，成功码为 `200`。该接口只读取 Gateway 自身的会话、执行器和任务数据，不调用 Bus，不新增 RPC，不写业务状态。

## 6. 数据流

1. 用户打开“状态检测”页面，页面不自动执行检测。
2. 用户点击“立即检测”。
3. 客户端在工作线程并行执行本机检测、各店铺只读检测和 Gateway 诊断请求。
4. 单项完成即写入内存结果；所有结果通过 Tkinter 主线程一次性渲染，避免页面频繁跳动。
5. Gateway 不可用时，本机和闲鱼实例结果仍正常展示，Gateway 相关项标记 `unknown`。
6. 用户点击处理按钮后，才调用现有启动、重新登录或更新逻辑。

检测结果仅保存在当前客户端内存中，退出软件后不保留。

## 7. 错误处理

- 每个网络请求使用明确超时，超时只影响当前检测项。
- 网络或 DNS 故障不能触发 Cookie 清理，也不能判定账号无权限。
- 商品管理接口返回登录过期时，登录项异常、权限项未知。
- Gateway Token 无效时，Gateway 相关项未知或异常，但继续完成本机检测。
- 某个店铺检测异常不能中止其他店铺。
- 诊断接口返回内容必须按 Token 授权范围过滤，避免跨代理商数据泄露。

## 8. 验证

客户端自动测试覆盖：

- 状态严重度汇总和未知状态统计。
- 单项超时及异常隔离。
- Outbox 数量和最老事件年龄分级。
- 商品列表成功、空列表、无权限、登录过期和网络失败。
- 多店铺结果互不串店。
- Gateway 失败时保留本机检测结果。

Gateway 自动测试覆盖：

- 无 Token、Token 过期和越权店铺。
- 单设备执行器匹配。
- 同店铺双设备在线。
- 本机在线但不是执行器。
- 任务失败、失败后恢复和无近期任务。

手工验证覆盖 Windows 单店、多店、双机、断网、Cookie 失效、无商品管理权限及 Outbox 积压场景。
